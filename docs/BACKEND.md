# 백엔드 규칙 (liaison-back)

- **담당:** 백엔드 코드 소유자(`.github/CODEOWNERS`). 각자 맡은 파트를 직접 고칩니다. 고칠 때는 PR로 올리고 백엔드 코드 소유자가 승인합니다.
- **공통 문서가 먼저입니다.** 모든 파트가 지킬 규칙은 `docs/common/`(liaison-docs)에 있습니다. 이 문서는 백엔드에만 해당하는 규칙을 적습니다. 공통 문서와 다르면 공통 문서를 따르고, 공통 규칙을 바꿀 일이면 liaison-docs에 PR을 올립니다.
- **공개 저장소입니다.** 사람 이름, 운영 서버 주소·계정, 탐지 기준값, 비밀값을 적지 않습니다.

## 1. Java 이름 규칙

공통 이름 규칙(DB 테이블·컬럼, API 필드, enum, 시각, 기본 키, 외래 키)은 `docs/common/CODE_CONVENTIONS.md` 1장을 따릅니다. 이름 자체는 `docs/common/GLOSSARY.md`가 기준입니다.

| 대상 | 규칙 | 예 |
|---|---|---|
| Java 클래스·엔티티 | PascalCase 단수 | `Membership`, `TeacherAssignment` |

- 예약어나 Java 기본 클래스와 겹치는 이름은 쓰지 않습니다. 예: 반은 `Class`가 아니라 `ClassGroup`

## 5. Flyway 마이그레이션
- **파일 이름:** `V<버전>__<무엇을_하는지>.sql`. 버전은 파일을 만든 시각을 UTC 연월일시분초 14자리로 적고, 설명은 영어 snake_case입니다. 예: `V20261123053005__create_consent_documents.sql`
  - 버전은 `date -u +%Y%m%d%H%M%S`로 얻습니다. 한국 시간이 아니라 UTC입니다(서버·DB와 같은 기준).
  - 세 자리 순번(`V001`)은 쓰지 않습니다. 두 PR이 같은 번호를 쓰는 일을 없애기 위해서입니다(운영자 결정, 11/23).
  - Flyway `out-of-order`는 끈 채로 둡니다(기본값). 새 DB(CI·로컬)·개발 서버·운영이 모두 같은 순서로 적용해야 하기 때문입니다.
  - 그래서 main에 내 파일보다 늦은 버전이 먼저 병합되면, 병합 전에 PR 브랜치를 main으로 갱신하고 내 파일 이름의 시각을 지금 시각으로 바꿉니다. 아직 병합하지 않은 파일이라 체크섬 문제가 없습니다.
  - main에 병합된 파일은 이름도 내용도 고치지 않습니다(Flyway 체크섬이 깨짐). 고칠 일은 새 파일로 합니다.
  - 자동 검사: 테스트(`MigrationFileNameTest`)가 이름 형식, 실제로 있는 날짜·시각인지, 지금보다 미래가 아닌지, 버전이 겹치지 않는지 봅니다. CI는 PR이 더한 파일의 버전이 main의 마지막 버전보다 뒤인지 봅니다.
